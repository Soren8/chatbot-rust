# Privacy levels and coding-agent connections

**Status:** implementation plan; no privacy-selection or agent-connection feature is implemented by this document. Cross-project direction: sibling `../../ai-platform-design/design.md`. Companion sandbox plan: `../../.devcontainer/CODING_AGENT_SERVICE_PLAN.md`.

## Goal and boundaries

First make saved-chat privacy choices enforceable. Then allow an eligible, authenticated user to add an external connection to the **operator's personal** OpenCode service. Both stages should be testable without a running OpenCode instance; the first must ship independently of the second. Starting agent runs and rendering tool activity is a later integration, not a prerequisite for connection configuration.

Private and Non-private describe **where conversation content may go**, not how `chatbot-rust` encrypts saved history: both continue to use the current client-derived key and AEAD redb store. Private is the default for new and existing authenticated sets. Non-private is a user opt-in allowing providers or harnesses whose retention/plaintext transcript handling does not qualify for Private. A guest chat remains RAM-only **in this application**; an external free-tier model may retain guest prompts, so the guest UI must not claim incognito or global Ephemeral behavior. Recoverable key custody and selectable never-on-disk Ephemeral sets are deferred.

## Shared service contract and parallel work

The sandbox-side team can implement OpenCode's authenticated listener and private host transport while the chatbot-side team implements privacy policy and mocks the connection API. These work streams do not need each other's running service. The v1 service is **not multi-tenant**: it uses one personal sandbox with all of the operator's workspace and tool credentials. Initial chatbot eligibility is a deployment-configured owner username only, plus an authenticated session, a valid per-request chat key, and a Non-private set for any later agent run. No ordinary logged-in or premium account inherits this access.

The agent service's contract is `kind=opencode`, private HTTPS/tunnel **base URL** reachable from the chatbot backend, HTTP Basic username/password, an approved server-side project directory (initially `/workspace/chatbot-rust`), and the OpenCode version's verified `/global/health`, `/session`, `/session/{id}/prompt_async`, `/event`, `/session/{id}/message`, `/session/{id}/abort` subset. Its HTTP API also provides dangerous file, shell, config, and auth operations: **never build a browser-facing raw proxy** or accept an arbitrary path/directory header from a client. The service team verifies exact 1.18.32 shapes from the installed binary's `/doc`; the chatbot team tests against a fake service and accepts a real connection only after that handshake. Direct browser-to-service CORS and credentials are out of scope.

## Stage A: persisted set privacy and provider classification

### A1. Specify types and deployment defaults

Introduce a closed `Private | NonPrivate` domain type; reject unknown serialized values. In `chatbot-core/src/config.rs` add an explicit privacy classification to each `ProviderConfig` (proposed YAML `privacy_level: private | non_private`). Missing classification means **non_private**, including the fallback provider. This protects against a typo or new provider becoming Private-eligible by omission. Retain independent free/premium tier checks; pricing/account tier and privacy eligibility are separate dimensions. Mark known qualified *example* local routes `private` in `.config.yml.example`; leave remote examples `non_private` until an operator actually verifies account/endpoint retention. `xai_zdr: true` or `store: false` alone is not evidence of full provider ZDR.

Deployers must explicitly classify their real providers before enabling Private-by-default requests; if the selected/default model is ineligible and no approved model exists, return a clear policy error **without a provider call or hidden fallback**. Validate enum values and example config (`config_example_has_no_unknown_keys`), and bump `.config-version` when a deployment actually requires new config keys. Keep service URLs/passwords out of example values and Git history.

Treat each egress receiving conversation content as a destination: Brave and native xAI search have their own retention implications; so do STT/TTS backends if content leaves the trusted local service. Decide and document which local voice-service paths meet Private, and classify or disable unverified external paths. A model's Private tag does not automatically approve its optional search tool. Guest providers retain their current tier policy but must not be described as ZDR without classification.

### A2. Persist the choice without exposing private metadata

Use authenticated **set identity**, not account-wide preferences or a client-supplied `encrypted` boolean, as the authority. `chatbot-core/src/history/types.rs` currently has no privacy field on `SetSnapshot`, `SetSummary`, `SetPage`, or `PrepareCapture`. `history/store/` supports legacy whole-set ciphertext and chunked `SETS_HEADER`/manifest/pairs; `list_sets` reads the sealed `SETS_NAME` row without loading the conversation. Design a versioned **sealed set descriptor** (name + privacy) in or alongside that row, bound by AEAD to user and set ID. Read legacy sealed name rows as `Private` without eagerly rewriting every history blob. Do not add a readable privacy flag or sensitive name to plaintext `SETS_META`; do not add a second conflicting canonical privacy value to both old whole-blob and chunked headers.

Extend `HistoryService` for one authoritative read used by list/load/prepare and for CAS-checked mode mutation. Creation and default-set creation choose Private. Forks inherit source mode and never implicitly upgrade it; legacy migration reads Private. All normal history commits and renames must preserve the descriptor. A mode change must update sealed data **atomically with set version/CAS**, invalidate cached summary/snapshot, and work for both whole-blob and chunked formats. A chunked set's manifest binds its ciphertext to the set version: use the existing snapshot commit or equivalent atomic reseal so a privacy-only version bump cannot break future loads. Ensure `PrepareCapture` and leased generation carry the validated mode and target version rather than consulting the currently selected set mid-stream.

### A3. Enforce before any model or tool call

In `chatbot-core/src/session.rs`, `chatbot-server/src/chat.rs` and `regenerate.rs`, resolve the authenticated target set and key through the existing ownership/prepare path; apply eligibility **after resolving the model (including the default) and the set, but before** provider construction/search dispatch or any request that sends text. Return a distinct 403/policy error for an incompatible model/tool, not a saved assistant error turn. Preserve existing key-validation and tier error behavior. Refuse unknown, deleted, other-user, or stale set IDs; do not trust privacy sent by the browser.

Set switching, regenerate, retries, fallbacks, forked histories, memories and system prompts must remain bound to the initiating set. Mode edits must reject while that set's generation lease is active (or serialize with the same lease); avoid a check-then-dispatch window where a mode changes between approval and outbound use. Reject forged use of an unapproved search backend even when the model itself qualifies. If a voice backend is unverified, indicate unavailability for Private rather than silently sending text/audio there. This stage should preserve current chat protocol and voice behavior for eligible destinations, not replace the generation or playback pipelines.

### A4. Shared UI and mode change

Return mode from `/get_sets`, `/create_set`, `/fork_set`, and `/load_set`; keep version in their existing responses. Add a CSRF-protected authenticated `POST /set_privacy` taking `{set_id, expected_version, privacy_level}`, validated using the per-request encryption key. Return the normal `409 version_conflict` shape on stale edits. Require an explicit confirmation and explanatory copy when moving Private → Non-private; on a switch back to Private, explain that the restriction applies only to **future transmissions** and cannot revoke previous provider retention. Show `🔒 Private` on saved sets and a text-only `Non-private` choice with the plain-language retention/tool-transcript disclosure. A guest chat is labeled "Temporary in this app" instead of "Ephemeral".

Filter/disable options based on the selected set's mode **and** account tier, with an explanation of unavailable models/search/voice paths. If `last_model` is incompatible after switching sets or migrating an old set, do not send a request or silently pick another provider; ask the user to choose an eligible one. Use the existing `static/chat.js`, `static/conversation-state.js`, set-generation fencing, `static/templates/chat.html`, and styles. Desktop and Capacitor should use the same UI flow; the native wrapper only needs a new APK if a native resource changes, whereas server-pulled assets require a webserver rebuild.

### A5. Verification and release

First add focused red tests for legacy descriptor/default, private-to-non-private CAS and conflict, chunk migration/manifest integrity, fork inheritance, cold/warm cache equivalence, other-user denial, and in-flight mode change. Then cover authenticated HTTP with an instrumented fake provider/search backend: incompatible model/search/default and forged payloads perform **zero outbound calls**; Non-private/eligible requests still work. Cover stale client set selection and reload in the existing JS behavior tests and run `js_syntax`. Test local/ZDR examples and `.config.yml.example` validation. Run targeted `testctl` package/target selections from `AGENTS.md`; do not narrow away a known failure. Update `docs/design-privacy.md` and relevant configuration docs to distinguish storage encryption from provider retention before committing. Deployment rollout must set eligible provider classifications before new Private-default requests; coordinate schema/version and host config deployment with `iac`.

## Stage B: user-managed connections to the coding-agent service

Start this stage only after Stage A has a reliable server-owned set privacy mode. It can be developed against a mock service independently of the sandbox team's network rollout. The first service is owner-only and Non-private; support for separate per-user OpenCode workers is another project, not an inference from adding a connection form.

### B1. Operator-approved service catalog

Add an **optional** application configuration section for coding-agent service profiles, e.g. `agent_services: [{id, kind: opencode, base_url, owner_username, project_directory, privacy_level: non_private}]`. Only the operator can change destinations, eligible account(s), and approved project roots. The example config has no live endpoint or credential; no profiles means no connections UI and no network calls. Validate unique IDs, private HTTPS/transport policy, supported kind and path, and fail closed on unknown kinds. Config is deployment topology, not a dynamic source of user-provided HTTP URLs. Extend `ConfigSource`/`AppServices` with an explicit owned catalog for isolated router tests; do not read a mutable global or `.env` unexpectedly in those tests.

The user's "Add connection" form selects an **approved profile ID**, enters a friendly label and that service's Basic username/password, and cannot enter an arbitrary URL or filesystem path in v1. This is intentional: an arbitrary user-controlled target behind a server-side proxy permits SSRF against the VPS's metadata, Docker, or internal services. A future personal-URL feature would require a dedicated outbound policy and DNS/redirect controls. The owner profile and server's native password are not tenant-level authorization: validate the authenticated owner on *every* connection and future run request, including after password resets, stale sessions, and owner changes. A connection cannot make Private tasks eligible.

### B2. Per-user encrypted credential storage

Do **not** add the service password to `UserStore` preferences/`users.json`, the server config, a browser-readable bootstrap blob, a URL, or logs. Add a narrow user-owned connection store behind the existing `HistoryService` redb handle (or another explicitly owned encrypted service if tests show a reason), with a separate AEAD key derivation/AAD binding **user ID + connection ID + blob kind** and the user's already validated per-request `EncryptionKey`. Store label/credential encrypted; store only opaque lookup/ownership metadata in plaintext. List without decrypting other users' rows; delete and rotate credentials without leaking previous values. The backend may use the secret during an authenticated request, but never returns it to the browser. Guest and absent/invalid enc-key requests are denied; persisted connections cannot be used for unattended background runs without a separate key-custody design.

### B3. HTTP/UI contract and transport verification

Add scoped routes such as `GET /agent_connections` (redacted labels, profile and last-checked status; no outbound call), `POST /agent_connections` (create), `PATCH /agent_connections/{id}` (label/secret rotation), `DELETE /agent_connections/{id}`, and `POST /agent_connections/{id}/check`. Writes and checks require the existing session, CSRF and per-request key; every read also verifies account/connection ownership. Bound body size, count of connections, timeout and response bytes. `check` calls only the server-approved base URL's `GET /global/health` using HTTP Basic over private authenticated transport, without following redirects or forwarding cookies, client headers, directory parameters, or arbitrary OpenCode routes. Return bounded status/version/capability errors; do not expose raw OpenCode error bodies or Basic challenges to the browser. Missing agent service is an ordinary unavailable state, not a failure of `/chat` or home rendering.

Show a Connections section in the shared chat UI for eligible logged-in users, with add/test/rotate/remove controls, a clear **Non-private** label and the note that OpenCode may persist plaintext sessions on its host. Never inject credentials into `static/templates/chat.html` or `APP_DATA`. Reuse CSRF, error presentation, and Android WebView cookie behavior; do not create a separate native-only client protocol.

### B4. Tests and integration handoff

Use a local fake Basic-auth server and explicit owned services in integration tests. Test profile allowlist, owner/other-user/guest denial, bad/rotated credentials, deleted connection reuse, CSRF, enc-key failure, malicious IDs/URLs, redirects, backend timeout, oversized responses, credential redaction, encrypted-at-rest bytes, concurrent writes, and offline service behavior. Ensure no raw OpenCode route is reachable through the app and that a Private set cannot start an agent run even with a valid connection. Target relevant `chatbot-core`/`chatbot-server` tests and `js_syntax` through `testctl`; the full CI suite remains the release gate.

The final smoke test, **after human deployment of the sandbox listener and private route**, is: owner logs in, selects an existing Non-private set, adds the pre-approved profile with a Basic password, checks health, and sees only redacted metadata; another user and any Private set remain barred. Confirm an unavailable agent host leaves ordinary chat and voice unaffected. The later run/streaming feature must map remote session IDs to owner + connection + set, use OpenCode's session-message snapshot to recover after SSE reconnect, and reuse the current voice mode without directly exposing OpenCode to the browser. That work is outside this connection-preparation stage.

## Decisions to resolve before implementing Stage B

- Which operator account may use the personal sandbox, which private network URL it will use, and which exact project root(s) the first service permits. Do not publish a live hostname, password or account credential in this plan.
- Whether connections are explicitly selected per Non-private set or from an owner-level default. Neither choice can override the set privacy policy, and no connection is automatically assigned to existing sets.
- How the independent speech/search retention classifications apply when an agent response is read aloud. A local voice service and a third-party TTS endpoint do not have identical guarantees.
