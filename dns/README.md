# Bridge-local DNS

The Compose `dns` sidecar polls the Linux host's resolver files through read-only `/etc` and `/run` directory mounts every two seconds. Voice-service and tests use its pinned bridge address (`172.29.0.53`) through Compose `dns:`. Webserver uses host networking to keep browser/Tailscale traffic out of Docker NAT, and bind-mounts `dns/host-resolv.conf` read-only over `/etc/resolv.conf`; the host can reach the sidecar's bridge IP directly. Docker ignores `dns:` in host mode.

Override `DNS_SUBNET` and `DNS_ADDRESS` together if that subnet conflicts, and recreate the Compose default network when changing the subnet. The tracked resolver file contains the default address, not a Compose template: when overriding `DNS_ADDRESS`, set `WEB_RESOLV_CONF` to a host file containing `nameserver <DNS_ADDRESS>` before recreating webserver. The voice service publishes `127.0.0.1:5100` for the host-networked webserver; configure `voice_service_host: localhost` and use `localhost` rather than `host.docker.internal` for host-based providers.

It selects up to three non-loopback nameservers, including systemd-resolved and NetworkManager uplinks when the primary resolver is a loopback stub. Queries fail over in order via UDP or TCP; no public DNS fallback or per-domain split-DNS routing is provided. When no host upstream is usable, queries receive no answer. Only `/etc` and `/run` resolver paths are supported; other symlink targets are unreadable. The broad read-only mounts include host files and sockets, so the sidecar runs unprivileged with only `NET_BIND_SERVICE` and a read-only root filesystem.

For this host-network rollout, update the existing provider/voice host settings, then run on the host: `docker compose build webserver` followed by `docker compose up -d --force-recreate webserver voice-service dns`. The webserver rebuild is required because templates and scripts are copied into its image.

Run `python3 -m unittest discover -s dns/tests -t dns -v` from the repository root. Before `docker compose run --rm tests`, start the sidecar with `docker compose up -d --build dns`; one-off `run` does not reliably start its DNS dependency. The host test executor runs its own test containers and does not use this Compose service.
